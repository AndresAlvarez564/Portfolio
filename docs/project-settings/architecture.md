## Overview

The Portfolio CRM is a serverless web application built on AWS that serves two primary purposes:

1. **Public Portfolio Website** — A professional showcase for recruiters, clients, and visitors to view projects, experience, skills, certifications, and contact information.
2. **Private Admin Panel** — A protected content management system where Andres can create, edit, and manage all portfolio content without editing code.

This architecture demonstrates a production-ready serverless application with authentication, CRUD operations, media management, database design, event-driven workflows, and AWS best practices.

### Architecture Principles

- **Serverless-first:** Pay-per-use model with automatic scaling and no server management
- **Security by design:** Private S3 buckets, Cognito authentication, least privilege IAM, backend authorization
- **Cost-optimized:** DynamoDB on-demand billing, Lambda ARM64, CloudFront caching, S3 lifecycle policies
- **Well-Architected:** Follows AWS Well-Architected Framework pillars (operational excellence, security, reliability, performance efficiency, cost optimization)
- **Infrastructure as Code:** All resources defined in AWS CDK with TypeScript for repeatability and version control
- **Event-driven:** Asynchronous processing for emails and notifications using SQS and EventBridge

### Component Connection Flow

#### Public Portfolio Flow

```text
1. User visits portfolio.example.com
   ↓
2. CloudFront serves React SPA from S3
   ↓
3. User browses projects (data fetched from API Gateway)
   ↓
4. API Gateway → Lambda (projects) → DynamoDB
   ↓
5. Response returns published projects only
   ↓
6. User views project screenshots served via CloudFront from S3
```

#### Admin Panel Flow

```text
1. Andres navigates to portfolio.example.com/admin
   ↓
2. Enters credentials on login page
   ↓
3. Frontend calls Cognito (via AWS Amplify)
   ↓
4. Cognito validates credentials and returns JWT tokens
   ↓
5. Frontend stores tokens and redirects to admin dashboard
   ↓
6. Admin creates/edits project
   ↓
7. Frontend calls API Gateway with JWT in Authorization header
   ↓
8. API Gateway validates JWT with Cognito Authorizer
   ↓
9. Lambda validates admin group membership
   ↓
10. Lambda writes to DynamoDB
   ↓
11. Lambda returns success response
   ↓
12. Frontend shows confirmation message
```

#### Contact Form Flow  

```text
1. Visitor fills contact form on public site
   ↓
2. Frontend calls POST /contact (no authentication required)
   ↓
3. API Gateway → Lambda (contact-handler)
   ↓
4. Lambda validates input (honeypot, rate limit, length)
   ↓
5. Lambda saves message to DynamoDB (status: unread)
   ↓
6. Lambda sends message to SQS queue
   ↓
7. Lambda returns success to frontend
   ↓
8. SQS triggers Lambda (email-worker)
   ↓
9. Email worker reads message from queue
   ↓
10. Email worker sends notification via SES to Andres
   ↓
11. SQS deletes message from queue (success)
   ↓
12. If SES fails, message goes to Dead Letter Queue for retry
```

#### Media Upload Flow

```text
1. Andres uploads screenshot in admin panel
   ↓
2. Frontend calls POST /media/upload (authenticated)
   ↓
3. API Gateway validates Cognito JWT
   ↓
4. Lambda generates pre-signed S3 URL
   ↓
5. Lambda returns pre-signed URL to frontend
   ↓
6. Frontend uploads file directly to S3 using pre-signed URL
   ↓
7. Frontend calls POST /media/confirm with S3 key
   ↓
8. Lambda saves media metadata to DynamoDB
   ↓
9. CloudFront serves media via public CDN URL
```

## Key Architectural Decisions

### 1. Serverless Architecture

**Decision:** Use serverless services (Lambda, DynamoDB, S3, API Gateway) instead of traditional servers (EC2, RDS, containers).

**Reasoning:**
- **Cost efficiency:** Pay only for actual usage, not idle server time
- **Automatic scaling:** Handles traffic spikes without manual intervention
- **No server management:** Focus on application logic, not infrastructure maintenance
- **High availability:** Built-in redundancy across multiple availability zones
- **Fast iteration:** Deploy individual functions without full application restarts

**Trade-offs:**
- Cold start latency for infrequently used Lambda functions (mitigated with provisioned concurrency if needed)
- Vendor lock-in to AWS (acceptable for portfolio demonstration project)
- Learning curve for serverless patterns (valuable skill for AWS career positioning)

---

### 2. DynamoDB with Single-Table Design

**Decision:** Use DynamoDB with a single table and composite keys (pk, sk) instead of multiple tables or a relational database.

**Reasoning:**
- **Performance:** Single-digit millisecond latency for all queries
- **Cost:** Pay-per-request billing with no minimum cost
- **Scalability:** Automatic scaling to handle any traffic level
- **Flexibility:** NoSQL model supports evolving data structures
- **AWS integration:** Native integration with Lambda, API Gateway, and CloudWatch

**Data Model Pattern:**
```text
Entity: PROJECT
pk = PROJECT#<project-id>
sk = METADATA
entityType = PROJECT

Entity: EXPERIENCE
pk = EXPERIENCE#<experience-id>
sk = METADATA
entityType = EXPERIENCE

Entity: CONTACT_MESSAGE
pk = CONTACT#<message-id>
sk = MESSAGE#<timestamp>
entityType = CONTACT_MESSAGE
```

**GSI Strategy:** xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
- `gsi-entity-type`: Query all entities by type (e.g., all projects)
- `gsi-status`: Query entities by status (e.g., published projects only)
- `gsi-featured`: Query featured projects for homepage

**Trade-offs:**
- Requires careful access pattern planning upfront
- No ad-hoc SQL queries (acceptable for well-defined use cases)
- Learning curve for NoSQL modeling (valuable skill for serverless applications)

---

### 3. Cognito for Authentication

**Decision:** Use Amazon Cognito User Pool instead of custom authentication or third-party services (Auth0, Firebase).

**Reasoning:**
- **Native AWS integration:** Seamless integration with API Gateway authorizers
- **Security features:** Built-in password policies, MFA, account recovery, token management
- **Cost:** Free tier covers up to 50,000 monthly active users
- **Compliance:** SOC, PCI DSS, HIPAA eligible
- **User groups:** Built-in role-based access control (admin group)

**Configuration:**
- User pool with email-based login
- Admin group for Andres (only admin group members can access admin panel)
- App client with USER_PASSWORD_AUTH flow
- JWT tokens (ID token for API authorization)
- Optional MFA for production

**Trade-offs:**
- AWS-specific implementation (acceptable for AWS-focused portfolio)
- Limited customization of hosted UI (using custom React login page instead)

---

### 4. S3 + CloudFront for Frontend Hosting

**Decision:** Host React SPA on S3 with CloudFront distribution instead of Amplify Hosting, Vercel, or Netlify.

**Reasoning:**
- **Cost:** S3 storage is extremely cheap, CloudFront has generous free tier
- **Performance:** Global edge locations for low-latency access worldwide
- **Security:** Private S3 bucket with Origin Access Control (OAC), HTTPS enforcement
- **Control:** Full control over caching behavior, custom headers, error pages
- **Integration:** Native integration with AWS CDK for infrastructure as code

**Configuration:**
- Private S3 bucket (no public access)
- CloudFront Origin Access Control (OAC) for secure S3 access
- CloudFront distribution with HTTPS only
- Custom error response: 404 → /index.html (React Router support)
- Cache behavior: index.html no-cache, assets with long TTL
- Automatic CloudFront invalidation after deployment

**Trade-offs:**
- Manual CloudFront invalidation required after deployment (automated in pipeline)
- No built-in preview deployments (acceptable for single-user admin)

---

### 5. Asynchronous Email Processing with SQS

**Decision:** Use SQS queue for email notifications instead of sending emails directly from API Lambda.

**Reasoning:**
- **Reliability:** Decouples email sending from API response, prevents timeout issues
- **Retry logic:** Automatic retries with exponential backoff for failed emails
- **Fault tolerance:** Dead Letter Queue (DLQ) captures failed messages for investigation
- **Performance:** API responds immediately without waiting for SES
- **Scalability:** Queue buffers messages during traffic spikes

**Implementation status:**
- Contact submissions are saved in DynamoDB before queueing.
- `portfolio-<stage>-contact-queue` triggers `portfolio-<stage>-email-worker`.
- The email worker sends SES notifications using `SES_FROM_EMAIL` and `SES_TO_EMAIL`.
- `portfolio-<stage>-contact-dlq` receives messages after three failed processing attempts and has a CloudWatch depth alarm.

**Flow:**
```text
API Lambda → SQS Queue → Email Worker Lambda → SES
                ↓ (on failure)
           Dead Letter Queue
```

**Trade-offs:**
- Slightly more complex architecture (acceptable for production-ready demonstration)
- Email delivery is asynchronous, not immediate (acceptable for notifications)

---

### 6. AWS CDK with TypeScript

**Decision:** Use AWS CDK with TypeScript instead of CloudFormation YAML, Terraform, or Serverless Framework.

**Reasoning:**
- **Type safety:** Compile-time error checking for infrastructure code
- **Reusability:** Create custom constructs for repeated patterns
- **Abstraction:** Higher-level constructs reduce boilerplate
- **AWS native:** First-class support for all AWS services
- **Developer experience:** IDE autocomplete, refactoring, testing

**Structure:**
```text
infra/
├── bin/app.ts                    # CDK entry point
├── lib/
│   ├── app-stack.ts              # Main application stack
│   ├── app-stage.ts              # Deployment stage wrapper
│   ├── pipeline-stack.ts         # CI/CD infrastructure
│   └── constructs/               # Reusable infrastructure modules
│       ├── auth.ts               # Cognito configuration
│       ├── database.ts           # DynamoDB tables and indexes
│       ├── lambdas.ts            # Lambda functions and permissions
│       ├── api.ts                # API Gateway configuration
│       ├── frontend-hosting.ts   # S3 + CloudFront
│       ├── monitoring.ts         # CloudWatch alarms and dashboards
│       ├── security.ts           # IAM policies, Parameter Store (optional)
│       └── async-processing.ts   # SQS, EventBridge
└── config/
    ├── dev.ts                    # Development environment settings
    ├── staging.ts                # Staging environment settings
    └── prod.ts                   # Production environment settings
```

**Trade-offs:**
- Requires TypeScript knowledge (acceptable for TypeScript-focused portfolio)
- AWS-specific (acceptable for AWS Solutions Architect positioning)

### 7. CodeDeploy for Lambda with Traffic Shifting

**Decision:** Use AWS CodeDeploy for Lambda deployments with canary releases instead of direct Lambda updates.

**Reasoning:**
- **Safety:** Gradual traffic shifting detects issues before full rollout
- **Automatic rollback:** CloudWatch alarms trigger automatic rollback on errors
- **Zero downtime:** No service interruption during deployments
- **Production best practice:** Industry-standard deployment pattern
- **Monitoring integration:** Validates deployment health with metrics

**Configuration:**
- Lambda versions and aliases (`live` alias)
- CodeDeploy deployment group per Lambda
- Deployment strategy:
  - **Dev:** All-at-once (fast feedback)
  - **Staging:** Linear10PercentEvery1Minute (validation)
  - **Prod:** Canary10Percent5Minutes (safe rollout)
- CloudWatch alarms for automatic rollback (errors, duration)

**Trade-offs:**
- Slightly slower deployments (acceptable for safety)
- More complex CDK configuration (valuable learning experience)

---

### 8. Multi-Environment Strategy

**Decision:** Use three environments (dev, staging, prod) with environment-specific configurations.

**Reasoning:**
- **Development isolation:** Test changes without affecting production
- **Pre-production validation:** Staging environment mirrors production
- **Cost optimization:** Dev uses cheaper settings, prod uses production-grade settings
- **Risk reduction:** Changes flow through dev → staging → prod

**Environment Differences:**

| Setting | Dev | Staging | Prod |
|---|---|---|---|
| Removal Policy | DESTROY | RETAIN | RETAIN |
| DynamoDB PITR | Disabled | Enabled | Enabled |
| Lambda Memory | 256 MB | 512 MB | 512 MB |
| Lambda Timeout | 10s | 15s | 15s |
| Log Retention | 1 month | 3 months | 12 months |
| Alarms | Basic | Enabled | Enabled |
| CodeDeploy | All-at-once | Linear | Canary |

**Trade-offs:**
- Higher AWS costs for multiple environments (acceptable for professional portfolio)
- More complex deployment pipeline (valuable experience)

---

### 9. Pre-Signed URLs for Media Uploads

**Decision:** Use S3 pre-signed URLs for direct browser uploads instead of uploading through Lambda.

**Reasoning:**
- **Performance:** Files upload directly to S3, bypassing Lambda
- **Cost:** No Lambda invocation time for file transfer
- **Scalability:** No Lambda payload size limits (6 MB synchronous, 256 KB response)
- **Simplicity:** Browser handles upload progress and retry logic

**Flow:**
```text
1. Frontend requests upload URL from Lambda
2. Lambda generates pre-signed S3 URL (valid for 5 minutes)
3. Frontend uploads file directly to S3 using pre-signed URL
4. Frontend confirms upload to Lambda
5. Lambda saves media metadata to DynamoDB
```

**Trade-offs:**
- Requires two API calls instead of one (acceptable for better performance)
- Pre-signed URL expiration requires error handling (standard practice)

### 10. Monitoring and Observability

**Decision:** Implement comprehensive monitoring with CloudWatch Logs, Metrics, Alarms, Dashboards, and X-Ray tracing.

**Reasoning:**
- **Operational visibility:** Understand system behavior in production
- **Proactive alerting:** Detect issues before users report them
- **Performance optimization:** Identify bottlenecks and slow queries
- **Debugging:** Trace requests across distributed services
- **Cost tracking:** Monitor Lambda invocations and DynamoDB consumption

**Monitoring Strategy:**
- **Logs:** Structured JSON logs from all Lambda functions
- **Metrics:** Custom metrics for business events (project created, contact form submitted)
- **Alarms:** Error rate, duration, throttles for all Lambda functions
- **Dashboards:** Operational dashboard with key metrics
- **Tracing:** X-Ray for request flow visualization xxxxx

**Required Alarms:**
- Lambda error rate > 1% for 5 minutes
- Lambda duration > 80% of timeout
- Lambda throttles > 0
- API Gateway 5XX errors > 1%
- DynamoDB throttled requests > 0

**Trade-offs:**
- Additional CloudWatch costs (acceptable for production-ready system)
- More complex CDK configuration (valuable operational experience)

## Security Architecture

### Defense in Depth

1. **Network Security**
   - Private S3 buckets (no public access)
   - CloudFront Origin Access Control (OAC)
   - API Gateway resource policies (optional)

2. **Authentication & Authorization**
   - Cognito User Pool for authentication
   - JWT tokens for API authorization
   - API Gateway Cognito Authorizer
   - Backend validation of user groups (admin-only endpoints)

3. **Data Protection**
   - HTTPS only (CloudFront, API Gateway)
   - Encryption at rest (S3, DynamoDB default encryption)
   - Encryption in transit (TLS 1.2+)

4. **Access Control**
   - IAM least privilege for Lambda execution roles
   - Cognito groups for role-based access
   - S3 bucket policies (deny public access)
   - API Gateway resource policies (optional)

5. **Application Security**
   - Input validation (backend)
   - Output encoding (frontend)
   - Rate limiting (API Gateway throttling)
   - CORS configuration (API Gateway)
   - Honeypot field (contact form)
   - IP-based rate limiting (contact form)

6. **Monitoring & Incident Response**
   - CloudWatch Logs for audit trail
   - CloudWatch Alarms for anomalies
   - X-Ray for request tracing
   - Automated rollback (CodeDeploy)

### Secrets Management

- **Parameter Store:** Configuration, environment variables, API endpoints
- **Secrets Manager:** Optional - only if third-party API keys are needed
- **Environment Variables:** Lambda configuration (non-sensitive only)
- **Never in code:** No secrets in Git repository, CDK code, or frontend

## Scalability Considerations

### Automatic Scaling

All services scale automatically without manual intervention:

- **Lambda:** Concurrent executions scale to account limits (1,000 default)
- **DynamoDB:** On-demand billing scales to any traffic level
- **API Gateway:** Handles 10,000 requests per second per region
- **S3:** Unlimited storage and requests
- **CloudFront:** Global edge network scales automatically
- **SQS:** Unlimited throughput

### Performance Optimization

- **CloudFront caching:** Reduces origin requests by 80%+
- **DynamoDB Query (not Scan):** Single-digit millisecond latency
- **Lambda ARM64:** 20% better price-performance than x86
- **API Gateway caching:** Optional for frequently accessed endpoints
- **S3 Transfer Acceleration:** Optional for large file uploads

### Cost at Scale

Estimated monthly cost for different traffic levels:

| Traffic Level | Requests/Month | Estimated Cost |
|---|---|---|
| Low (MVP) | 10,000 | $5-10 |
| Medium | 100,000 | $20-40 |
| High | 1,000,000 | $100-200 |

Cost breakdown:
- Lambda invocations: $0.20 per 1M requests
- DynamoDB: $1.25 per million write requests, $0.25 per million read requests
- API Gateway: $3.50 per million requests
- CloudFront: $0.085 per GB (first 10 TB)
- S3: $0.023 per GB storage, $0.0004 per 1,000 GET requests
