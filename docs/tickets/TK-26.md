## Objective
Implement the case study routes and the corresponding public case study section on the project detail page and the admin case study editor.

## Proposed Scope
- Backend: `GET /projects/:id/case-study` (public) and `PUT /projects/:id/case-study` (admin, upsert)
- Frontend public: case study section rendered inside the project detail page
- Frontend admin: case study editor tab or section inside the project edit page
- Observability: structured logs for case study operations (shares the projects Lambda)

## Flow

```
Public: GET /projects/{id}/case-study
↓
Lambda GetItem pk=PROJECT#<id> sk=CASE_STUDY
↓
If not found → return empty object (not 404, case study is optional)
↓
Return case study fields

Admin: PUT /projects/{id}/case-study
↓
Lambda validates admin group
↓
Validates body: problem, solution, architecture (required), challenges, results (optional)
↓
PutItem pk=PROJECT#<id> sk=CASE_STUDY (upsert — creates or replaces)
↓
Returns saved case study
```

## Acceptance Criteria
- `GET /projects/{id}/case-study` returns case study data if it exists
- `GET /projects/{id}/case-study` returns empty object if no case study exists (not 404)
- `PUT /projects/{id}/case-study` creates or replaces the case study
- `PUT /projects/{id}/case-study` returns 403 without admin group
- `PUT /projects/{id}/case-study` returns 400 if required fields are missing
- Project detail page renders case study section when data exists
- Project detail page hides case study section when data is empty
- Admin case study form saves and pre-fills correctly
- All unit tests pass

## Notes
- Case study is stored as a separate DynamoDB item with the same `pk` as the project (`PROJECT#<id>`) and `sk=CASE_STUDY`
- This allows fetching project + case study in a single Query on `pk=PROJECT#<id>` if needed
- Case study is optional — not every project needs one
- The upsert uses PutItem (full replace), not UpdateItem — simpler and sufficient for this use case
